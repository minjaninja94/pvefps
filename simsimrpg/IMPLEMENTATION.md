## A. 건드리면 안 되는 게임 규칙(매 작업 전 재확인)

- 한 화면/한 공간/채널별 멀티 채팅+공동 자동사냥. 별도 마을, 인스턴스 사냥터, 던전 화면 생성 금지.
- 게임오버·리셋·웨이브 종료 없음. 계속 성장하는 캐릭터형 MMORPG.
- 유닛 랜덤 소환·합성·덱 운영 없음. 플레이어 본체의 클래스·전직·스킬만 성장.
- **32개 전 진영/진영별 6개 기초 계보=192개**, 1~3차 이진 분기 2,880개 직업노드 + 4~7차 해당 계보의 고유 상위 직업/전술 전문화를 포함하는 **총 9,024개 직업노드/1,536개 7차 최종 직업**의 전체 정식 버전 설계 목표. 일부만 공개하고 완료라 주장 금지.
- 한 번 만든 캐릭터의 진영, 초기 직업 계보, 기본 외형은 변경 불가. 이후 같은 계보 내에서만 영구적인 상위 전직 선택 가능.
- 부캐 무수히 생성할 수 있으나 **계정당 채널 표시 + 자동사냥(오프라인 포함) 활성화는 오직 1캐릭터**.
- 모든 아이템 자동 비교 → 높은 등급 즉시 장착 → 교체된 장비와 나머지 드롭 자동 판매/골드 환산. 인벤토리 제한/슬롯 과금 없음. 거래 없음.
- 세션이 끊겨도 서버는 마지막 활성 캐릭터 한 명만 시간을 계산해 경험치·골드·아이템 축적.
- PC 입력 횟수 기반 보너스는 추후 선택형. '다른 앱의 실제 키 입력 내용' 수집 절대 금지.

## B. 파일·서비스 구성 제안

```text
pvefps/
├── desert-strike/             # 절대 수정 금지
├── goablo/                    # 절대 수정 금지
└── simsimrpg/
    ├── PLAN.md                # 최신 결정 기준
    ├── CLASS_CATALOG.md       # 32진영·192기초 클래스·다단계 전직 규칙
    ├── IMPLEMENTATION.md      # 이 문서
    ├── src/                   # 이후에 생성할 게임 코드
    ├── assets/                # 이후에 생성할 도트 에셋
    ├── database/              # 이후에 생성할 SQL·마이그레이션
    └── tools/                 # 이후에 생성할 검증·에셋 빌드도구
```

- 정적 웹: Cloudflare Pages 별도 프로젝트. Build root/include paths는 **simsimrpg/**에만 한정. 게임마다 별도 빌드/배포. 기존 Cloudflare Pages 프로젝트의 설정/제한량에 영향 최소화.
- 실시간 채널: Cloudflare Worker + Durable Object로 접속/캐릭터 위치/간단 전투·메시지 동기화. 채널 하나 = 하나의 공용 전장.
- 계정/영속성: 별도 Supabase Auth + PostgreSQL. 기존 데저트 프론트 Supabase DB와 테이블·키·권한 분리.
- 웹 게임: TypeScript + Phaser 기반 도트 렌더링, UI 모달/채팅/직업 트리. 모바일 반응형/PWA.
- PC 보조 앱(선택): 별도 릴리스, 개인정보 보호된 키 활동 통계와 저부하 미니뷰. 게임 기본 동작은 보조 앱 없이 가능.

## D. 데이터 모델 초안

```text
accounts(id, created_at, last_active_character_id)
characters(id, account_id, faction_id, root_class_id, base_appearance_id,
           current_job_id, level, experience, gold, state_version, created_at)
active_characters(account_id UNIQUE, character_id UNIQUE, activated_at,
                  generation, last_settled_at, channel_id)
factions(id, name, theme)
class_roots(id, faction_id, name, battle_role)
class_jobs(id, root_class_id, parent_job_id, tier, branch_key,
           display_name, active_skill_refs, passive_skill_refs, gfx_refs)
character_job_choices(character_id, class_job_id, chosen_at, UNIQUE(character_id, tier))
skill_mastery(character_id, skill_id, rank, points)
equipment_slots(character_id, slot, item_instance_id)
loot_events(id, character_id, settlement_id, item_roll, resolution, gold_delta)
hunt_settlements(id, character_id, activation_generation, range_start,
                 range_end, exp_delta, gold_delta, UNIQUE(character_id, activation_generation, range_start))
channels(id, name, wave, wave_state, theme)
channel_presence(channel_id, account_id UNIQUE, character_id, connection_state)
channel_messages(id, channel_id, sender_account_id, text, created_at)
```

실제 SQL 작성 시 FK/UNIQUE/CHECK/RLS, 트랜잭션 잠금 및 인덱스를 추가한다. 위 스키마는 기획용 예시이며 **마이그레이션이 실행된 상태가 아니다**.

## E. 필수 검증 시나리오

1. 한 계정에 조선/해병/랩터 부캐 3개 생성 → 첫 캐릭터만 온라인 및 오프라인 사냥, 나머지 둘은 성장 0.
2. A캐릭터 사냥 중 B로 전환 → A의 보상/레벨 정지, B만 진행, 채널에 A는 사라지고 B만 보임.
3. 한 계정 두 기기에서 동시에 활성화/전직 호출 → 서버에서 승인된 **단 1개 캐릭터·1개 전직 경로**만 유효, 보상 중복 없음.
4. 캐릭터 생성 후 진영/기초 클래스/기본 외형 직접 수정 API 요청 → 서버 거절.
5. 조선 검객에서 금위검사 선택 → 그 아래 금군검장/척사대장 노드만 등장, 유랑검호로 전환 불가; Lv.1 리셋 없음.
6. 같은 등급 상위 무기 획득 → 자동 장착 후 구무기 매각, 골드 1회 지급.
7. 하위 무기 1만 개 드롭 시뮬레이션 → 1만 개 장비가 인벤에 적재되지 않고 골드 합산, 렌더 성능 저하 없음.
8. 9시간 오프라인 → last_settled_at 기준 보상 한 번만 계산, 재로그인/새로고침/복수 클라이언트 반복해도 중복 지급 없음.
9. 웨이브 보스 실패 → 캐릭터 생존 기록·장비 그대로, 게임오버 없이 안정 구간에서 사냥 재개.
10. 32진영 × 6기초 루트 × 8말단 전직 경로 **총 1,536경로 모두 생성·전직·공격·정산 스모크 테스트**.
11. 공동 게이트 1개·도우미 3명·전중후열/측면 대형 + 채널 내 30~50명 도트 스프라이트·자동공격·채팅이 겹치는 성능 측정, 수용 인원은 결과에 따라 조정.
12. 기존 데저트 프론트 파일/DB/Cloudflare 배포에 변경이 없는지 비교.
